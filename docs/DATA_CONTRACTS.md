# Data contracts

P0.1 implements provider-neutral Python domain values in `shadow.domain` and deterministic validation/identity functions in `shadow.data`. They use only the Python standard library. Provider SDK, dataframe, HTTP, database, and LLM objects are not accepted as cross-system contracts; a future adapter must translate them before this boundary.

## Time and observation semantics

All accepted timestamps must be timezone-aware. Contract construction normalizes them to UTC; a naive timestamp is an explicit validation failure and is never assumed to be local time or UTC. `Provenance` and `DatasetMetadata` may retain source timezone and session descriptions without treating those strings as a trading calendar.

`Bar.observation_time` always means the **end of the represented interval**. It is neither an interval-start convention nor an unexamined provider timestamp. `availability_time` is a separate UTC instant: the earliest time a model may legally consume that record. Its `AvailabilitySemantics` is one of `provider_published`, `system_received`, or `modeled`. Availability cannot precede observation. This is a data contract only; P0.1 does not make decisions or simulate fills.

## Executable values and validation

`Instrument` is a non-empty trimmed provider-neutral identifier and `BarInterval` is a positive `timedelta`. `Provenance` identifies the observation source and may record source timezone/session context.

`Bar` has an instrument, explicit interval, observation and availability times, OHLC values, optional volume, availability semantics, and provenance. Prices must be finite `Decimal` values. Volume is optional because not every source supplies it; when present it must be finite and non-negative, including zero. Bars allow values such as negative prices where a market can legitimately produce them, but enforce `high >= open`, `high >= close`, `low <= open`, `low <= close`, and `high >= low`.

`Quote` has finite `Decimal` bid/ask prices, optional non-negative finite bid/ask sizes, time/availability fields, and provenance. Locked and crossed quotes are retained rather than repaired or rejected; `market_state` classifies them as normal, locked, or crossed. This preserves source evidence without claiming every quote is executable.

`DatasetMetadata` provides required source, dataset identifier, instrument scope, UTC coverage start/end, schema version, and optional interval, retrieval method, timezone/session, adjustment policy, declared validation status, and quality notes. Bar datasets must declare one matching interval; quote datasets must not. Records must be chronological by nondecreasing observation time, scoped to the declared instruments/source/coverage, and have unique observation identities. A bar identity is instrument, interval, and observation time; a quote identity is instrument and observation time. Validation never sorts malformed input, deduplicates, fills, interpolates, or repairs it. It does not infer expected observations: without an explicit market calendar, an absent interval is an unknown expectation rather than automatically invalid missing data.

Failures use `MarketDataValidationError` with an invariant name and, for collection checks, a record index.

## Numeric policy

P0.1 accepts `Decimal` at the domain boundary. This avoids binary-float representation differences while remaining standard-library-only and sufficient for deterministic research-data canonicalization. Adapter code must deliberately convert external numeric values. Decimal NaN and infinities are rejected. Canonical serialization renders all numerical zero, including `Decimal("-0")`, as `"0"`; equal finite Decimal values with different exponent/trailing-zero representation serialize identically, without rounding in the caller's mutable Decimal context. Integer fixed-point was not chosen because asset/source precision varies and no P0.1 scale contract exists.

## Canonical dataset identity

`canonical_dataset_bytes(observations, metadata)` first validates a non-empty homogeneous bar or quote sequence, then emits canonical UTF-8 JSON. Fields are written in documented fixed order, timestamps use UTC ISO-8601 with six fractional digits and `Z`, Decimal values use normalized fixed-point strings, and interval duration uses exact integer microseconds. Input must be chronological; equal-time valid records are sorted by their complete canonical record bytes so their incidental input order does not change identity. Duplicate observations are rejected before serialization.

`dataset_fingerprint` returns the lowercase hexadecimal SHA-256 digest of those bytes. The canonical metadata includes schema version, observation kind, source, dataset ID, retrieval method, sorted instrument identifiers, interval, coverage, source timezone/session, and adjustment policy. `quality_notes` and declared `validation_status` are deliberately excluded because they describe a delivery or its commentary, not the canonical observations or their interpretation; validation itself is always rerun before fingerprinting. The digest identifies these exact canonical bytes. It is not a claim about provenance truth, provider authenticity, or completeness.

The repository-owned JSON fixtures are synthetic, require no credentials or network access, and exercise valid bars/quotes plus out-of-order, duplicate, malformed-OHLC, and naive-timestamp failures. Their expected valid-bar digest is pinned in tests.

## P0.2A feature contracts

`shadow.features` accepts `Sequence[Bar]` plus `DatasetMetadata` and calls P0.1 `validate_bars` itself. Consequently a feature function does not accept quotes, dataframes, provider objects, malformed time order, duplicate bars, or mismatched dataset scope; it does not normalize them. Its output is a tuple of immutable `FeatureSnapshot` values aligned to the supplied bars, with the input sequence order retained.

Each snapshot identifies the provider-neutral `Instrument`, feature name, `close` input, `shadow.features.v1` implementation version, declared source dataset ID, observation time, availability time, and input-count window. The source dataset ID is retained as upstream lineage. P0.1's fingerprint of an entire delivery is intentionally not copied into every snapshot because appending later observations would then change an otherwise identical historical snapshot's lineage field.

Snapshot state makes lack of a number semantic: `ready` requires a finite `Decimal`; `warming_up` requires the reason `insufficient_history`; and `unavailable` has a named reason. There are no fabricated zero warm-up values. An invalid requested window or mathematical domain raises `FeatureComputationError`, so failure is distinct from non-readiness. P0.2A z-scores use `unavailable/zero_variance` when their denominator is zero.

All P0.2A primitives use bar `close`. The return primitive is one-period **simple return**, `(P_t / P_(t-1)) - 1`; its first same-instrument observation warms up and a zero prior close fails explicitly. Log returns were not added because the first mean-reversion feature kernel needs only the simpler, negative-price-compatible close-to-close primitive and logarithms would impose a positive-price domain. Rolling mean, variance, standard deviation, and z-score use strict full trailing windows. Variance is **population variance** (`ddof=0`), and z-score is `(current_close - rolling_mean) / population_standard_deviation` over that same full window.

Feature arithmetic stays in `Decimal`, using a new local context for every calculation (34 significant digits, `ROUND_HALF_EVEN`) rather than the mutable process-wide Decimal context. Finite result values are canonically normalized, including zero to `Decimal("0")`. This is the P0.2A numerical boundary: no float, NumPy, Pandas, or runtime numerical dependency is used.

For every ready or explicitly unavailable snapshot, its availability is `max(availability_time)` of the same-instrument input bars used for its trailing window; a warm-up snapshot uses the partial trailing history that establishes that it is not ready. Thus feature availability can lag the aligned bar's observation time, including when an earlier bar was published later. This is an availability rule, not an observation-order shortcut.

## P0.3 strategy signal contracts

`shadow.strategies` consumes P0.2A snapshots rather than market-provider values. The sole current strategy accepts only a matching ready close z-score at its configured rolling window and implementation version. At an explicit timezone-aware decision time, evidence is rejected if absent, not ready, for another instrument/feature/version/window, not yet available, or older than its configured freshness allowance. It emits either no signal, a `long_entry` proposal while supplied context is `flat` and `z_score <= entry_threshold`, or an `exit` proposal while context is `holding` and `z_score >= exit_threshold`.

Signals are immutable evidence, not orders: they retain the provider-neutral instrument, strategy and configuration identities, material thresholds/freshness allowance, decision and availability times, feature identity/window/version/value/observation/availability time, reason, and source dataset ID. They contain no size, price, broker, fill, risk authorization, or portfolio state. This is an unvalidated hypothesis contract, not evidence of profitability.

## P0.4A chronological simulation contracts

`shadow.simulation` consumes immutable upstream evidence rather than recalculating features or strategy rules. It models four narrowly scoped event kinds: `market_observation_available`, `feature_available`, `signal_available`, and `execution_opportunity`. Every event carries a UTC-normalized effective time, provider-neutral instrument, caller-supplied stable event ID, and source reference. A signal event additionally carries the immutable P0.3 `Signal` and must occur exactly at its signal availability time. A modeled execution opportunity contains no price, quantity, order type, or fill assertion.

`observation_time` remains the end of a represented market interval and is never substituted for availability. An upstream market or feature event has effective time equal to its availability time. `decision_time` is the explicit time at which P0.3 evaluated legal feature evidence; the P0.3 signal contract makes its `availability_time` equal to this decision time. An execution opportunity's `event_time` is its own modeled instant. These are distinct concepts even where a fixture gives them the same timestamp.

The canonical event key is `(effective_time, causal precedence, instrument identifier, event ID)`, ascending. Equal-time causal precedence is explicitly market observation, feature, signal, execution opportunity; the final two fields make ordering independent of input/provider/object/hash order. A signal establishes an exclusive eligibility boundary at its availability time. A same-instrument opportunity is legal only with `event_time > signal_availability_time`; equal timestamps are explicitly ineligible, so a completed-bar signal cannot use the close that produced it. A legal opportunity authorizes an execution attempt but is not a fill and does not consume the action. `TimelineRecord` gives structured evidence of each event or eligibility decision, including references/times for the signal and candidate opportunity and a machine-readable reason.

## P0.4B lifecycle contracts

`process_lifecycle` composes P0.4A's `process_timeline` output and is the exclusive owner of simulated position lifecycle state. For each instrument it returns an immutable `InstrumentLifecycleState` of `flat`, `pending_entry`, `holding`, or `pending_exit`; callers cannot supply a hidden mutable position. `LifecycleAction` is provider-neutral and records only stable action/signal references, instrument, entry/exit type, creation and exclusive eligibility time, and origin state. It contains no quantity, order type, price, time-in-force, broker ID, fee, or cash field.

The transition contract is `flat + long_entry -> pending_entry`, `pending_entry + P0.4A legal opportunity -> execution attempt`, `pending_entry + filled outcome -> holding`, `holding + exit -> pending_exit`, `pending_exit + P0.4A legal opportunity -> execution attempt`, and `pending_exit + filled outcome -> flat`. `unfilled` and `rejected` outcomes leave their compatible pending action unresolved. Opening creates one quantity-free `SimulatedPosition` with an authoritative `opened_at` time; closing removes it. Thus flat cannot have a position, holding/pending-exit has exactly one, and each pending state has exactly one compatible action. Equal-time opportunities remain ineligible because P0.4A remains authoritative. `LifecycleRecord` captures prior state, event identity/time, decision, reason, resulting state, related action/position, and any P0.5A attempt/outcome for reconstruction.

The initial one-position-per-instrument policy rejects entry while holding and suppresses duplicate entries/exits while their same-direction action is pending. Exit while flat and cross-state signals are explicit rejected records. Same-instant entry and exit signals for an instrument reject both regardless of input order. State is isolated by instrument. Pending actions have no invented timeout: `LifecycleResult.unresolved_actions` reports them at end of the supplied stream, and `open_positions` reports holdings including a pending exit. There is no forced end-of-data close, fill, price, or economic inference.

## P0.4C/P0.5A end-to-end simulation and execution contracts

`SimulationInput` is the small immutable composition input for the initial hypothesis: `DatasetMetadata`, a tuple of `Bar`, a non-empty tuple of P0.3 `MeanReversionConfig`, a required P0.5A/P0.5B `QuoteExecutionConfig`, optional P0.1 `Quote` evidence, optional P0.4A `ExecutionOpportunity` values, optional P0.5C economics configurations, and an optional caller `simulation_id`. The runner first calls P0.1 `validate_bars` exactly as supplied, then requires metadata to declare `validated` status. It never sorts, repairs, or deduplicates bars. One strategy configuration is permitted for each configured instrument, which preserves P0.4B's one authoritative lifecycle per instrument. `economics_configs=None` disables economics; an enabled tuple must contain exactly one configuration for every configured strategy instrument, without duplicates or extras, and is stored in canonical instrument order. The fixed z-score feature identity/version and `rolling_window` are the necessary feature configuration; no unrelated broker, portfolio, risk, or LLM configuration exists here.

The runner reuses P0.2 `calculate_z_scores` for each configured window and retains its immutable snapshots. One intended decision point exists for each configured instrument and feature-availability instant. If delayed delivery makes several snapshots available at that same instant, the snapshot aligned to the newest observation time is selected; earlier snapshots remain result evidence but do not emit duplicate backfill signals. At the decision instant the runner supplies the P0.4B state established by events at strictly earlier effective times. P0.4A's equal-time precedence puts feature events before signal events and opportunities, so a same-time opportunity cannot alter the strategy's state input and is still ineligible for the signal emitted at that instant. `flat` maps to P0.3 `PositionState.flat`, `holding` maps to `PositionState.holding`, and either pending lifecycle state suppresses evaluation and emits no signal. A ready, non-pending evaluation invokes the existing P0.3 function once; its `None` result is recorded as a valid no-signal disposition rather than an error. Warm-up and unavailable selected snapshots retain their P0.2 states/reasons and are recorded as not actionable. Invalid input/calculation remains an explicit exception.

P0.5A introduces immutable `ExecutionAttempt` and `ExecutionOutcome` values. An attempt records stable attempt/action/signal/opportunity references, instrument, lifecycle action type and execution side, eligibility boundary, opportunity/attempt times, and model identity. An outcome records exactly `filled`, `unfilled`, or `rejected`, a machine-readable reason, any exact P0.1 `Quote` market evidence used, and a finite execution price only for `filled`. `QuoteExecutionConfig` identifies `shadow.execution.quote_bid_ask.v2`, its explicit maximum market age, and `slippage_bps`. It compares freshness as `attempt_time - quote.observation_time`, separately from the causal requirement `quote.availability_time <= attempt_time`.

For a matching instrument, the execution model deterministically selects the newest causally legal quote by availability time, then observation time, then stable complete-quote reference. It never selects a later quote, caller order, midpoint, close, or favorable side. Entry is a buy at ask and the initial long-only exit is a sell at bid. Locked quotes remain usable according to P0.1; crossed quotes become explicit rejected outcomes. Missing, not-yet-available, or stale evidence becomes unfilled. Attempt consistency errors, including duplicate attempt IDs in batch resolution, mismatched action/opportunity instruments, time mismatch, or non-strict eligibility become rejected. Both unfilled and rejected attempts leave the lifecycle action pending under P0.5A.

`SimulationResult` is immutable structured simulation evidence, not a portfolio or performance result. Runner v3 contains the simulation implementation version/run label, source metadata and P0.1 bar fingerprint, canonical strategy configuration, P0.5A/P0.5B configuration and quote evidence, optional canonical P0.5C configurations, P0.2 implementation version, feature snapshots, one `StrategyEvaluation` per intended decision point, proposed signals, P0.4A `TimelineResult`, P0.4B `LifecycleResult`, the resulting attempt/outcome tuples, and P0.5C economic executions. It contains no explicit second spread charge, cash balance, portfolio accounting, P&L, return, equity, drawdown, or Sharpe field.

P0.4C/P0.5A lifecycle admission is an explicit research-simulation baseline pending the future independent risk engine; it is not a risk decision or production authorization. The current configuration has a threshold-driven exit but no maximum-holding parameter, so the runner deliberately does not infer a timeout from `opened_at`. Appending future quotes or future opportunities cannot change completed prior attempts/outcomes, timeline records, or lifecycle records; a later opportunity may only attempt or resolve an already-visible pending action after the compared prefix.

## P0.5B deterministic adverse slippage

`QuoteExecutionConfig.slippage_bps` is a finite nonnegative `Decimal`, defaulting to exact zero. No float conversion, estimation, randomness, or policy maximum exists. Numerically equivalent assumptions are canonically represented without Decimal-context arithmetic (including signed zero). The required freshness allowance is unchanged.

After P0.5A has selected the newest legal matching quote and established a fill, BUY uses `ask * (1 + slippage_bps / 10000)` and SELL uses `bid * (1 - slippage_bps / 10000)`. One basis point is 0.0001. Quoted spread is embedded exactly once; no midpoint or synthetic spread penalty is introduced. Zero returns the original side Decimal unchanged, including its representation. Nonzero arithmetic uses an isolated 34-significant-digit half-even context, explicit exponent limits -999999/+999999, and explicit traps. Rounding is bounded against the original baseline to prevent favorable movement on inputs with more than 34 significant digits. Rounding can create equal-price plateaus; increasing bps cannot improve price. Overflow/invalid arithmetic raises `ExecutionContractError`, never a new fill status.

P0.1 permits finite negative quotes. The specified percentage formula would improve negative executable prices, so nonzero slippage on such a baseline raises `ExecutionContractError`; zero retains P0.5A behavior. There is no 10000-bps cap: SELL scenarios at/above that value can reach zero/negative modeled prices. These are algebraic stress outputs, not assertions of feasible market execution. Negative quote handling and finite-context limits are numeric contract boundaries, not liquidity rules.

Every `ExecutionOutcome` now retains `execution_config` even when unfilled/rejected. For a fill, `baseline_execution_price` derives the executable side from the exact immutable `market_evidence` Quote, and `execution_price` holds the modeled price. The stable quote reference, attempt, model identity, and configuration reconstruct the price decomposition without redundant stored baseline values. The filled reason is `filled_at_quote` at zero or `filled_with_slippage` at nonzero bps. Unfilled/rejected status and absent prices remain unchanged. V2 emits `no_legal_quote` for both missing and not-yet-available evidence: v1's `quote_not_yet_available` diagnostic inspected future quotes and could rewrite a historical unfilled reason when future data was appended. That enum value remains readable for historical evidence, but v2 does not emit it. Stale, crossed, and attempt-rejection reasons are unchanged. Only `FILLED` transitions lifecycle state; a numeric contract exception aborts computation rather than producing misleading evidence.

`execution_sensitivity(attempt, quotes, config, slippage_scenarios)` returns a tuple of immutable outcomes sorted by ascending bps, preserving duplicate scenarios. It overrides only bps per scenario, materializes quote iterables once, and inserts no implicit zero scenario. Empty scenarios return an empty tuple. Each outcome carries its own configuration and the common attempt; input scenario/quote ordering cannot change equivalent evidence. Callers include zero when they want an explicit comparison baseline. Fixture values 0/1/5/10 bps are neither recommended assumptions nor SPY/QQQ estimates. There is no optimization or performance metric.

Model identity advances from `shadow.execution.quote_bid_ask.v1` to `.v2` because a filled price is no longer necessarily the quote price, and outcome evidence/reasons change. Configuration distinguishes zero and nonzero assumptions within v2; v1 attempts are not silently relabeled. Quote-reference Decimal exponent formatting is explicitly context-independent. `SimulationResult` already carries attempts, outcomes, configuration, selected quotes, and lifecycle records, so no new runner fields or authority changes are needed. Future bars, quotes, signals, and opportunities cannot rewrite completed outcomes; retries retain their own immutable configuration/evidence.

## P0.5C fixed quantity and fee economics

`shadow.execution.economics` is a separate downstream boundary. Its fixed model identity is `shadow.execution.fixed_quantity_fee_bps.v1`, representing one caller-declared quantity per instrument, unit multiplier one, a fee in basis points of absolute final executed notional, and deterministic Decimal arithmetic. It does not modify `shadow.execution.quote_bid_ask.v2` or take part in quote selection, fill validity, adverse slippage, or final modeled-price calculation.

`ExecutionEconomicsConfig` is frozen and contains `instrument`, `quantity`, `quote_currency`, `fee_bps`, and `economics_model_id`. Quantity must be a finite `Decimal` strictly greater than zero. It comes only from experiment configuration and is not generated by strategy, price, equity, cash, risk, or quote size. Fractional quantity support here is a research-domain abstraction and does not imply broker or venue support. The current unit/contract multiplier is fixed at one; there is no multiplier contract. Numerically equivalent quantities and fee assumptions have one canonical trailing-zero-free representation, including ordinary unsigned zero where zero is allowed.

`quote_currency` must be a non-empty trimmed string. It is an explicit caller-declared research denomination required to interpret the evidence; the current `Instrument` contract does not independently verify currency. P0.5C adds no hard-coded currency, FX conversion, or currency minor-unit rounding.

`fee_bps` must be an explicit finite nonnegative `Decimal`; exact zero is valid and there is no empirical default. The model is synthetic and deterministic. It does not claim to reproduce a broker schedule and has no fixed, per-share, minimum, maximum, maker/taker, regulatory, venue-specific, or rebate term.

For final modeled execution price `p`, declared quantity `q`, and fee bps `b`, P0.5C computes:

```text
signed_notional = p * q
gross_notional = abs(signed_notional)
fee_rate = b / 10000
fee = gross_notional * fee_rate
BUY execution_cash_flow = -signed_notional - fee
SELL execution_cash_flow = signed_notional - fee
```

All arithmetic uses a fresh explicit context with 34 significant digits, `ROUND_HALF_EVEN`, exponent limits -999999/+999999, and trapped invalid operation, division-by-zero, overflow, and underflow failures. It never uses float or cent/currency quantization and does not depend on the caller's Decimal context. Signed numerical zero is canonicalized to ordinary zero. A numeric failure raises `ExecutionEconomicsError` and does not rewrite the preserved execution outcome as rejected.

`EconomicExecution` embeds the full immutable `ExecutionOutcome` and its `ExecutionEconomicsConfig`, plus calculated `gross_notional` and `fee`. Instrument, side, final execution price, quantity, quote currency, attempt reference, signed notional, and execution cash flow are read-only derived properties. The full outcome remains evidence because one attempt may have distinct P0.5B sensitivity outcomes. This is one economically described fill, not a paired `TradeRecord`, cash balance, settlement ledger, buying-power value, portfolio equity, or realized P&L.

Only `filled` outcomes can produce an `EconomicExecution`; `unfilled` and `rejected` outcomes produce none and incur no ordinary execution fee. Fees use the final P0.5B modeled price, so quote-side spread and slippage are already represented and are not deducted again. P0.5B can produce zero or negative prices in declared stress scenarios. P0.5C preserves those outcomes, takes the absolute executed notional as its nonnegative fee base, and maintains algebraic BUY/SELL cash-flow signs. Such evidence is stress-domain output and does not establish ordinary market feasibility; later evaluation must not silently treat it as an ordinary observation.

P0.5C has no feedback into features, strategy, chronology, opportunities, quote selection, fill status/price, retry behavior, or lifecycle transitions. It also adds no sizing authority, liquidity assertion, partial fills, market impact, portfolio accounting, P&L, or broker behavior. Future input extensions cannot rewrite prior economic executions, and repeated equivalent inputs reproduce identical evidence.

## P1A trade reconstruction and historical evaluation

`shadow.evaluation.reconstruct_trades` accepts only a `SimulationResult` whose P0.5C economics configuration is enabled. It is a reconciliation boundary, not a second simulator: its result is derived solely from immutable supplied timeline, lifecycle, execution, economics, and final-state evidence. It requires exact unique coverage of events, lifecycle records, attempts, outcomes, economics executions, configured instruments, final states, unresolved actions, and open positions. Filled outcomes require exactly one economic execution; unfilled/rejected outcomes are retained separately and never become a trade.

Each completed `TradeRecord` pairs a filled long entry and filled long exit only through the same authoritative `SimulatedPosition.opening_action_id`. Entry and exit must have the same instrument, fixed quantity, and caller-declared quote currency; partial closes and FX conversion are not modeled. Both fills must retain the action/attempt/opportunity chain, exact lifecycle transition, matching execution-model configuration, causally available quote, and quote freshness under that configuration. Evaluation fails closed instead of accepting altered, stale, future, duplicate, omitted, or orphaned evidence. Final pending/open lifecycle states remain incomplete; P1A never creates a synthetic end-of-stream exit.

For a completed trade with entry price `p_in`, exit price `p_out`, fixed quantity `q`, entry fee `f_in`, and exit fee `f_out`, P1A uses the deterministic Decimal formulas:

```text
gross_result = (p_out - p_in) * q
total_fees = f_in + f_out
net_result = gross_result - total_fees
gross_return = gross_result / entry_gross_notional
net_return = net_result / entry_gross_notional
```

The return denominator and both returns exist only when entry and exit prices are strictly positive. If either price is zero or negative, the trade is `stress_price` evidence: gross/net monetary algebra and fees remain visible, but ordinary returns and aggregate performance inclusion are prohibited. Ordinary totals are grouped strictly by the caller-declared quote currency and provide gross, fee, and net sums plus win/loss/flat counts; P1A never mixes currencies or presents a portfolio total.

`ExperimentManifest` requires SHA-256 fingerprints for the validated bar dataset, supplied quote multiset, supplied execution-opportunity multiset, strategy configuration, execution configuration, economics configurations, and complete supplied simulation evidence. It also records feature/simulation implementation versions, caller-supplied code revision, optional caller labels, an evaluation-model identity, and mandatory limitations. Canonical identity is independent of incidental evidence order and mutable Decimal context, retains duplicate supplied evidence, and does not claim authentication or unavailable generator identity. Quote evidence deliberately has no dataset-level provenance metadata in `SimulationResult`.

## P2A paper risk contracts

`OrderIntent` is immutable and provider-neutral. It retains operational scope, the complete source `Signal`, instrument, BUY/SELL side, finite requested quantity, source-derived intent time, operational quantity-configuration identity, paper target, market semantic, and DAY time-in-force. `OrderIntent.from_signal` maps `long_entry` to BUY and `exit` to SELL and always uses the signal decision time, so consumer time cannot rewrite the proposal. The quantity configuration is operational and independent of P0.5C research economics.

`RiskPolicy` explicitly identifies the policy/model and declares enabled state, canonically ordered allowed instruments, whole positive maximum order quantity, positive maximum concurrent positions, and four nonnegative freshness allowances. `OperatorControls` and `RiskState` carry separate observation/availability times; state also carries scope, identity/revision, inventory completeness, canonically ordered open long positions, and outstanding operational orders/authorizations. Empty complete inventory means flat; incomplete inventory does not.

`RiskDecision` embeds the intent and retains canonical status/reasons, policy identity/fingerprint, state identity/revision/fingerprint, stable supporting feature/quote references, explicit decision time, model version, deterministic decision identity, and an optional prior-decision reference. Equivalent policy/state collection order and ambient Decimal context cannot alter equivalent evidence.

`AuthorizedOrder` is a compact immutable application capability issued only after the gate has recorded an authorized decision and installed its reservation. It identifies its scope, intent payload, decision, and grant and carries a private gate-local token. A future supported paper adapter receives an intent only through `RiskGate.claim_for_dispatch`; raw upstream objects and reconstructed historical evidence are insufficient, and one artifact cannot be claimed twice. This is an in-process API guarantee rather than a cryptographic security boundary.
